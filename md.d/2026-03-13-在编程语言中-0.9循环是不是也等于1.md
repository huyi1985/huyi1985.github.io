# 在编程语言中，0.9循环是不是也等于1？

前几天写了篇小文，《反直觉！-1 和 1 之间所有小数之和是多少？不是 0 吗？》，没想到引起了不少留言评论。这背后的数学知识我是真不懂，只是从这个在数学上反直觉（可能数学家觉得本该如此吧）的问题，想到了计算机中的**能模拟实数的浮点数**在指定范围内求和的问题。

严格来说，浮点数还不是实数或有理数的子集，因为数学中（至少）没有 `NaN`（Not a Number）这个（其实是一组）特殊的数字吧。但如果编程语言里少了 `NaN`，那就连基本运算都不得不 `try-catch` 了。

比如，假设没有 `NaN`，`sqrt(-1)` 要等于几？本以为加上了内置的复数类型就万事大吉了。那 `if sqrt(-1) < sqrt(-2)` 应该是 `true` 还是 `false` 呢？

这两天又想到了另一个有点反直觉的数学问题，不过老生常谈了：

**0.999999……（0.9 循环）是不是等于 1？**

![](/assets/km70yp.webp)
**0.9 循环 = 1** 这在数学上是成立的。那在编程语言里呢？

结论就有点意思了。**主流编程语言中**，简单的数学表达式**全都算出了 1**，**任意精度计算器/代码库，反而“算错”了**。

## 用电脑计算 `1/9*9`

我试了几种主流编程语言，计算 `1/9*9`，得到的答案都是 **1.0**。

因为这些通用编程语言底层都遵循着 **IEEE 754** 双精度浮点数标准。`1/9` 的结果是 `0.1111111111111111`（16 位有效数字），再乘以 9，浮点运算的舍入机制恰好把结果"凑"回了 `1.0`。

但这个“正确答案”，其实是**两次舍入误差恰好互相抵消**的结果，歪打正着了。

有趣的是，如果换成**任意精度**的计算工具（比如 `bc`），结果反而不是 `1` 了。

`bc` 是 Unix/Linux 系统自带的**任意精度（arbitrary precision）计算器**。用 `scale` 设置小数精度：

```bash
$ echo "scale=10; 1/9*9" | bc
.9999999999

$ echo "scale=50; 1/9*9" | bc
.99999999999999999999999999999999999999999999999999
```

无论 `scale` 设多大，结果都是 `.` 之后一堆 `9`，永远到不了 1。哪怕把 `scale` 设到 1000：

```bash
$ echo "scale=1000; 1/9*9" | bc
.9999999999999999999999999999999999999999999999999...（共1000个9）
```

哪怕设置为最大值 `scale=2147483647`：

```bash
$ echo "scale=2147483647; 1/9*9" | bc
Fatal error: Out of memory for malloc.
```

bang！直接把内存耗尽了！

“世界上最好的语言”PHP 的 `bcmath` 扩展也是任意精度：

```php
echo bcmul(bcdiv("1", "9", 50), "9", 50);
// 0.99999999999999999999999999999999999999999999999999
```

结果同样是一串 `9`，永远差那么一丁点到不了 `1`。

顺带提一句， `bcmath` 扩展的维护者之一是位可爱的小姐姐。

![PHP bcmath 扩展维护者之一 Saki Takamachi](/assets/5x5vry.webp)

## 为什么任意精度反而"错"了？

这里的关键在于：**任意精度并不是无限精度**。

`bc` 的 `scale=50` 意味着保留 50 位小数。`1/9` 的精确结果是无限循环小数 `0.111111……`，但 `scale=50` 之后会**截断**为 50 位：

```
0.11111111111111111111111111111111111111111111111111
```

这已经不是精确的 `1/9` 了，它比 `1/9` 小了那么一丢丢。再乘以 9，自然得不到 1，只能得到：

```
0.99999999999999999999999999999999999999999999999999
```

而 IEEE 754 浮点数虽然精度只有约 15-17 位有效数字，但它的舍入规则是**四舍五入到最近的可表示值**（round to nearest, ties to even），两次运算的舍入误差恰好互相抵消，反而得到了数学上正确的结果。

这就出现了一个很有意思的现象：**精度更低的浮点数算对了，精度更高的任意精度库反而算错了**。

如果真的想得到精确结果，需要使用**有理数**（分数）类型。比如 Julia 语言的有理数（`Rational{Int64}`）运算：

```julia
# `1//9`表示分数1/9，乘以9得到`9//9`，化简为`1//1`
julia> 1//9 * 9
1//1
```

或者，Python 的 `fractions` 模块也可以做到：

```python
from fractions import Fraction
print(Fraction(1, 9) * 9)
# 1
```

有理数类型不做小数展开，直接用分子分母进行运算，所以不存在截断问题。

## 顺带提一下 0.1 + 0.2 不等于 0.3 的问题

浮点数的“经典名场面”，`0.1 + 0.2`，在大多数主流语言中的结果都是：

```
0.30000000000000004
```

Python、JavaScript、Java、Ruby、C……无一例外。但又是“世界上最好的语言”PHP，PHP 竟然意外算“对”了：

```php
<?php
echo 0.1 + 0.2;
// 0.3
```

这其实是因为 PHP 默认的显示精度（`php.ini` 配置中的 `precision=14`）会对输出做四舍五入。内部存储的值实际上和其他语言一模一样：

```php
<?php
printf("%.17g", 0.1+0.2);
// 0.30000000000000004

var_dump(0.1 + 0.2 == 0.3);
// bool(false)

echo bcadd("0.1", "0.2", 1);
// 0.3
```

所以 PHP 只是"看起来算对了"，内心和其他语言一样挣扎。

----

浮点数的世界就是这么有趣：**精度不够的时候可能歪打正着，精度提高了反而差之毫厘**。想要数学上的精确，最终还是得回到分数.

毕竟，计算机和数学家看问题的方式，终究是不一样的。
