# 早期Unix中的“隐藏”命令——glob

在类 Unix 系统中，大多数命令（可执行文件）都存放在 `/bin`、`/sbin`、`/usr/bin` 和 `/usr/sbin` 等目录中。而 `/etc` 目录则主要用于存放系统和应用程序的配置文件。

但你能想到吗——早期 Unix 中竟然还有存放在 `/etc` 目录中的命令？

假设当前目录下有 `x.c`、`y.c`、`z.c` 和 `Makefile` 这几个文件。要统计所有 C 语言源文件的行数，我们大概会下意识地敲出：`wc -l *.c`，对吧？

通配符 `*` 实在太好用了，以至于我们很少去思考一个更深层的问题：

当输入 `*.c` 时，**是谁**把它展开成了 `x.c y.c z.c`？

或者说，难道所有命令（`ls`、`wc`、`cp`、`rm`……）都要各自重新实现一套解析 `*.c` 的逻辑——遍历目录、逐一匹配文件名吗？

不要重复造轮子！这是软件开发中的一条经验法则。**今天**，是由 **Shell** 来负责展开通配符的。这就是为什么我们经常会在一些工具的配置文件中看到 `bash -c "command"` 这种写法，其实就是为了让 Shell 来处理通配符。

但在**早期的 Unix 世界**里，情况完全不同。那时的计算机性能有限，PDP-7、PDP-11 上的主存储器都⾮常小，留给用户程序的只有可怜的几 KB，通配符展开这种“繁重”的工作无法被整合进 Shell，而是交由一个独立的小程序来完成——它的名字叫 **`glob`**。

本文开头提到的那个不在 `bin` 目录里的命令，正是被放在 `/etc` 下的 `glob`。glob 一词代表 “global”，意为“全局”。

![Unix V6 程序员手册中 glob 的介绍](/assets/q5zb5e.webp)

如果你在 1970 年代的 Unix 终端中敲下 `wc -l *.c` ，那么系统真正执行的命令相当于：

```bash
glob wc -l *.c
```

`glob` 会先扫描当前目录，找出所有匹配 `*.c` 这个模式的文件——`x.c`、`y.c`、`z.c`——再把这些文件名作为参数，传递给 `wc` 命令。也就是说，`glob` 会逐个检查文件名，看它们是否符合通配符规则，然后再把匹配的文件名传递给最终要执行的命令：

```bash
glob wc -l *.c 
# → wc -l x.c y.c z.c
```

`glob` 的主要功能由两个函数实现：`expand()`（第 45 行）和 `execute()`（第 50～53 行）。`expand()` 会遍历当前目录，收集所有匹配通配符的文件名，并将它们存放在数组 `ava` 的第 2 个及之后的元素中，而 `ava[1]` 则存放要执行的命令本身，如 `wc`、`rm` 等。`execute()` 则通过系统调用 `execv()` 来执行这些命令。

可以把 `glob` 看作是 **辅助 Shell 展开通配符的工具**。在早期资源受限的情况下，`glob` 相当于 Unix 系统上的又一种**预处理器**。

Unix 上当时有不少预处理器，如 C++ 最初版本的 `cfront`，可理解为 C 语言的面向对象预处理器；再比如，`bc` 计算器可以看作 `dc` 计算器的预处理器，因为 `dc` 的后缀表达式对新手来说太不直观了。

随着机器性能的提升，加之预处理器变得稳定且可靠，其功能就会逐渐被整合进主要程序中，预处理器本身也随之消失。`glob` 最终被吸收到 Shell 中，成为了 Shell 的内置功能。

今天，Python、Go 和 Ruby 等语言中还依然提供名为 `glob()` 的函数，而从模式生成文件名扩展列表的操作被称为 **“globbing”**，也衍生自 glob 这个词。
