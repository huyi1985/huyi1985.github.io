# 反直觉！-1和1之间所有小数之和是多少？不是0吗？

昨天看到一个帖子，说到了一个数学上答案反直觉的问题。

![](/assets/nepme5.webp)

“`[-1, 1]` 内所有实数相加，结果等于几？”

答案是，结果取决于计算顺序，而且在现有的数学框架内，**无法证明答案为 0**！

对于 `[-1, 1]` 内任意一个小数，乘以 `-1` 就能得到它的相反数，二者相加必然为 0。明明看起来就是如此，但结果却不是 0，真是反直觉啊。

**那 `[-1, 1]` 之间的所有浮点数之和是不是 0 呢**？

浮点数与数学上的实数有一个**关键的差异**：浮点数只能表示有限个实数，而不是数轴上的每一个点。最著名的例子应该就是 `0.1 + 0.2 != 0.3` 了吧。之所以结果等于 `0.30000000000000004`，就是因为 `0.1` 和 `0.2` 在二进制下存储时被截断，累积的舍入误差导致结果偏离了的直觉。

计算机中的浮点数遵循 IEEE 754 标准，有 32 比特（位）的单精度和 64 比特的双精度两种格式。它们的**本质是有特定结构的二进制数**——1 位符号位、若干位指数位、若干位尾数位。

那么只要穷举所有 32 比特或 64 比特的二进制数，把每个二进制数重新解释为浮点数（注意，这不是把整数 `x` 转成 `x.0` 那种类型转换，而是直接按 IEEE 754 的规则解读），再筛出其中位于 `[-1.0, 1.0]` 的浮点数，对其求和看看结果是不是 `0.0` 不就行了。

看似是一个 `for` 循环就能解决的简单问题，而且结果显然不就是 `0.0` 吗？因为（有限的）正负浮点数是对称的——每个正浮点数 `x`，把符号位翻转就得到 `-x`，二者相加为 `0.0`。但实际遇到的问题却比想象的多得多。

## 遍历 2⁶⁴个浮点数应该很费时间吧

64 比特的双精度浮点数有 `2⁶⁴` 个，这个数有多大？`2⁶⁴ ≈ 1.8 × 10¹⁹`。所以遍历这么多个浮点数应该很费时间，也许需要好几个小时吧。

现代 CPU 主频 3GHz 左右，即每秒执行约 `10⁹` 量级的简单操作。即便每次循环只花 1 个时钟周期，也需要 `1.8 × 10¹⁹ / 10⁹ = 1.8 × 10¹⁰` 秒。这可不是几小时了，而是大约 **570 年**！所以**遍历所有双精度浮点数根本不现实**。

那单精度的浮点数呢？共有 `2³² ≈ 4.3 × 10⁹` 个，按同样的估算方法，遍历一遍大约只需要几秒钟。这个时间是完全可以接受的。那么我们就来遍历这 `2³²` 个二进制模式，取出其中位于 `[-1.0, 1.0]` 的所有浮点数，再对其求和。

参考代码（Rust 语言）如下：

![](/assets/xx21i4.png)

```rust
let mut count: u32 = 0;
let mut numbers: Vec<f32> = Vec::new();

let start = Instant::now();

for bits in 0..=u32::MAX {
	let f = f32::from_bits(bits);

	if (-1.0..=1.0).contains(&f) {
		count += 1;
		numbers.push(f);
	}
}

let elapsed = start.elapsed().as_secs_f64();

println!("=== Brute Force: all u32 -> f32 ===");
println!("Total patterns:  {}", 1u64 << 32);
println!("In [-1, 1]:      {count}");
println!("Collect time:    {elapsed:.3} seconds");
```

运行结果：

```
=== Brute Force: all u32 -> f32 ===
Total patterns:  4294967296
In [-1, 1]:      2130706434
Collect time:    6.041 seconds
```

## 结果竟然是 4194304！

接下来就可以按收集顺序逐个累加 `[-1.0, 1.0]` 之内的浮点数了：

![](/assets/sfulzf.png)

```rust
let mut sum32: f32 = 0.0;
let mut sum64: f64 = 0.0;
for &f in numbers {
    sum32 += f;
    sum64 += f as f64;
}

// 结果为：
// f32=4194304  f64=0.015625
```

用 `f32` 类型的变量做累加器，结果竟然是 `4194304`（即 `2²²`），和 `0` 差了十万八千里！即使用 `f64` 类型的变量做累加器，结果也相差了 `0.015625`，仍然不是 0。

既然 `0.1 + 0.2` 都跟 `0.3` 有误差，那这么多浮点数相加一定也有误差。也许按从小到大排序后再相加，误差会小些？

```
Sum (sorted):    f32=2122729.5  f64=-0.015625
```

但结果依然不是 `0`。

既然排序了，那是不是还可以借鉴高斯小时候计算 `1+2+...+100` 的思路——首尾配对？把最小的负数和最大的正数配对相加，第二小的和第二大的配对……`f32` 的正负数是精确对称的（`sorted[i]` 和 `sorted[n-1-i]` 互为相反数），每一对相加都等于 `0`，这回总该等于 `0` 了吧。

![](/assets/p7icgd.png)

```rust
for i in 0..n / 2 {
    let pair32 = sorted[i] + sorted[n - 1 - i];
    sum32 += pair32;
}
if n % 2 == 1 {
    sum32 += sorted[n / 2];
}
```

这回结果终于是 `0` 了，终于与直觉一致了。

## 几个有趣的现象与更多求和策略

在通过穷举 `[-1.0, 1.0]` 内所有单精度浮点数，来模拟这个反直觉的数学问题的过程中，我们可以看到几个有趣的现象：

* **浮点数的分布极不均匀**：全部 43 亿个 `f32` 中有近半数（21.3 亿个）分布在 `[-1, 1]` 之间。也就是说浮点数在靠近 0 的区域极其密集，越远离 0 越稀疏
* **求和顺序决定结果**：这与数学问题中"（无数个）实数求和取决于计算顺序"形成了有趣的呼应
* **精度不是万能的**：即便用 `f64`（双精度）做累加器，21 亿次累加后仍然有残余误差
* **“大数吃小数”问题**：当单精度的累加器的值达到 `2²⁴ = 16777216` 左右时，加上一个绝对值小于 `1` 的数就完全没有效果了

这个求 `n` 个浮点数之和的算法还能做什么调整呢？

**随机打乱后求和**：把 `[-1.0, 1.0]` 内的浮点数随机打乱顺序，再求和。由于正负数被随机穿插，部分抵消效果比朴素遍历好，但每次运行结果可能不一样——随机性带来了不确定性。

**Kahan 求和算法**：这是数值计算领域专门为减少浮点累加误差而设计的算法。用一个额外的补偿变量 `c` 来追踪每次加法中丢失的低位部分，在下一次加法时补回来：

![](/assets/j82ea7.png)

```rust
let mut sum: f32 = 0.0;
let mut c: f32 = 0.0;        // 补偿变量
for &f in numbers {
    let y = f - c;            // 补偿上次丢失的部分
    let t = sum + y;          // 加到累加器
    c = (t - sum) - y;        // 计算本次丢失的部分
    sum = t;
}
```
