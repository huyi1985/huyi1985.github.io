# SQLite 比文件系统快 35%：一场颠覆常识的性能实验

在大多数工程师的直觉里，"数据库"和"文件系统"从来不是同一个重量级的对手。文件系统是操作系统内核里最贴近硬件的一层，`open()`、`read()`、`write()` 几条系统调用就能摸到磁盘；而数据库要解析 SQL、维护 B-tree、处理事务日志，怎么看都是"重"的那一方。所以当 SQLite 官方在自己的网站上贴出一篇题为《35% Faster Than The Filesystem》的文章，声称把小文件直接存进 SQLite 数据库，比把它们存成磁盘上一个个独立文件还要快 35%，还要省 20% 的空间时，这个结论听起来更像是一句挑衅。

但这不是一次孤立的营销式实验，而是一条跨越十几年的研究线索的最新结果。

## 从"多大的 BLOB 才该存数据库"说起

这场争论最早可以追溯到 2006 年，微软研究院的 Jim Gray 发表了那篇被反复引用的论文《To BLOB or Not to BLOB: Large Object Storage in a Database or a Filesystem》。他给出的经验法则很朴素：小于 256KB 的对象适合放进数据库，大于 1MB 的对象适合放进文件系统，中间那段则要看读写比例和覆写频率而定。这篇论文的落脚点其实不在瞬时性能，而在于长期运维中的碎片化问题——他甚至为此发明了"storage age"（存储年龄，即对象被覆写的次数）这个概念，来标准化不同读写模式下的比较。

2011 年，SQLite 官方顺着这个思路做了一次自己的实验，发表在《Internal Versus External BLOBs》一文中。测试环境是 Ubuntu 上的 Ext4 文件系统，跑的是 2011 年的 SQLite 3.7.8。结果把 Jim Gray 的阈值大幅下修：以推荐的 8192 字节页大小为例，10KB 的 BLOB 存进数据库比存成文件要快 2.24 倍，20KB 快 1.87 倍，直到 100KB 左右两者基本打平，再往上文件系统才重新占优。这篇文章还顺带给出了一个至今仍然常被引用的建议：处理 BLOB 时，数据库页大小设成 8192 或 16384 字节综合表现最好。

如果故事到这里为止，结论无非是"小文件放数据库，大文件放磁盘"，算不上多有冲击力。真正让人意外的，是六年之后 SQLite 用 3.19.0 版本重新测了一遍——这次连"数据库更快"的下限本身都被往上推翻了一层：对于 10KB 左右的 BLOB，SQLite 不仅在读写两端都快，差距还扩大到了 35%。

## kvtest：一个只有一个 C 文件的测试工具

支撑这个数字的，是 SQLite 源码树里一个不起眼的命令行工具 `kvtest.c`。它和 SQLite 的 amalgamation（把整个引擎打包成单一 `sqlite3.c`/`sqlite3.h` 的发布形式）一起编译，产出一个名叫 `kvtest` 的可执行文件，只提供四个子命令：`init` 生成一个装满随机 BLOB 的测试数据库，`export` 把这些 BLOB 原样导出成磁盘上的独立文件（可选是否分层放进 `00/00/00` 这样的目录树），`stat` 查看数据库的基本状态，`run` 则是真正的压测入口。

```c
** kvtest init DBFILE --count N --size M --pagesize X
** kvtest export DBFILE DIRECTORY [--tree]
** kvtest run DBFILE [options]
```

`run` 命令里最值得玩味的是它对"数据库读取"给出的三种实现路径，一层比一层贴近硬件。第一种是最朴素的 SQL 语句 `SELECT v FROM kv WHERE k=?1`，预编译后循环绑参数执行；第二种换成 `sqlite3_blob_open()`/`sqlite3_blob_read()` 这套增量 BLOB I/O 接口，绕开 SQL 解析和查询执行的开销，直接操作页缓存；第三种则是把整个数据库文件通过 `PRAGMA mmap_size` 映射进虚拟内存，让读取变成对内存的直接访问。三种路径依次叠加优化，性能也依次爬升——在 Windows 上，第一种打法比直接读文件快 5 倍，到了 mmap 加持的第三种，优势能拉大到 10 倍以上。而所谓"35% 更快"这个更保守的数字，来自这条曲线上表现最不明显的一端：一台老旧的 Android 手机。

真正的实验规模其实相当扎实：五台跨度极大的机器——一台 2009 年的机械硬盘 Windows 7 笔记本、一台 2016 年的 SSD Windows 10 笔记本、一台 2015 年的 MacBook Pro、一台 32GB 内存的 Ubuntu 桌面机，外加一部 Galaxy S3 安卓手机——每台机器上都生成 10 万个大小在 8KB 到 12KB 之间随机分布、总量约 1GB 的不可压缩 BLOB，分别以数据库形式和独立文件形式存储，再逐一压测读写。

## 为什么"打开一次文件"比想象中更贵

真正的答案，藏在一个几乎被所有人忽略的系统调用成本里。用文件系统存储一万个小对象，意味着每次访问都要付出一次完整的 `open()` 和 `close()`；而用 SQLite，无论访问多少条记录，数据库文件只需要打开一次。`open()` 要经过路径解析、权限检查、inode 查找、文件描述符分配这一整套内核开销，这个成本几乎与文件内容大小无关——文件越小，这份"固定税"占的比例就越高。这也正是为什么阈值会随着 BLOB 变小而越来越偏向数据库：等到文件本身只有几十 KB 甚至几 KB 时，真正花在读写数据上的时间可能还不如打开和关闭文件描述符的时间长。

空间上的 20% 差距则是另一个更直白的原因：文件系统会把每个文件填充（padding）到分配单元（allocation unit）的整数倍，哪怕文件只比边界多出一个字节，也要占满下一个块；而 SQLite 把所有记录打包进同一批页面里，紧密排列，浪费的只是页内的碎片，不会像独立文件那样按块对齐浪费空间。

写入这一侧的故事更有意思，也更贴近真实世界的复杂性。无论用数据库还是直接写文件，写操作普遍比读操作慢 5 到 15 倍，这一点两边打平。但 Windows 默认开启的杀毒软件会让这场比赛变得不对称：因为杀毒软件要对每一个被写入的文件单独扫描，分散成上千个文件的写入会被拖慢一个数量级，而 SQLite 因为只写一个文件，几乎不受影响。反过来，如果对每个文件都强制调用 `fsync()`/`FlushFileBuffers()` 保证落盘，独立文件写入又会比数据库慢上 10 倍以上——因为 SQLite 可以把一整批写操作合并进一次事务提交，只在事务边界上做一次持久化，而不是每写一个文件就同步一次磁头。`kvtest` 里专门留了一个 `--multitrans` 选项来验证这一点：一旦强制让每次读写都单独开一个事务，SQLite 的优势会立刻消失,甚至反过来变慢——真正的秘密武器从来不是 B-tree 有多聪明,而是"批量事务"这四个字。

## 一个诚实的但书

SQLite 官方在文章末尾留了一段颇为克制的说明，值得原文引用其精神：35% 只是作者在自己手头几台设备上测出的近似值,会因硬件、操作系统、实现细节和随机波动而变化;确实有审阅者在自己的机器上测出了相反的结果,原因尚不明确;在文件系统缓存是冷的（cold cache）情况下，数据库的优势也会缩水甚至消失。作者给出的结论措辞相当谨慎——SQLite 的读写延迟"与直接文件 I/O 相当，常常更快，有时几乎一样快"，而不是一句可以到处套用的"数据库永远比文件系统快"。这份自我修正的坦诚，恰恰是这篇文章比大多数性能博客更值得信任的地方。

这个结论后来也得到了独立的第三方验证。2022 年有开发者用类似的方法论,在 Btrfs 和 Ext4 上重新跑了一遍真实工作负载下的对比测试（相关代码开源在 GitHub 的 dbench 项目中），得到的结论方向一致：SQLite 大致快出两倍左右。虽然具体倍数因测试方法而异，但"小对象存进单一数据库文件通常不吃亏，甚至更快"这个大方向，在十几年、多个团队、不同操作系统的重复实验里始终没有被推翻。

## 写在最后

把 Jim Gray 2006 年的 256KB 阈值、SQLite 2011 年的 100KB 阈值、和 2017 年这次 10KB 场景下 35% 的优势放在一条时间线上看，能发现一个有意思的趋势：这道分界线并不是一个物理常数，而是随着 SQLite 自身的优化不断向"文件系统"那一端推移——`SQLITE_DIRECT_OVERFLOW_READ` 编译选项、增量 BLOB API、mmap 支持，每一次工程改进都在蚕食原本属于裸文件 I/O 的优势区间。这提醒我们，很多"底层比上层快"的直觉，成立的前提其实是上层没有认真做优化；一旦数据库把系统调用开销这类"税"降到最低，它反而可以比自己所依赖的文件系统跑得更快。

对于真正需要落地的工程决策，这篇实验给出的建议其实很朴素：如果业务里的对象普遍偏小（缩略图、图标、配置片段、小型文档），把它们直接存进 SQLite，用增量 BLOB API 加上合理的页大小（8192 或 16384），批量提交事务，通常能同时省下磁盘空间和 I/O 时间，还顺带拿到了事务一致性和单文件备份的便利；而视频、高清图片这类大对象，依然应该老老实实交给文件系统去管。只是下一次再听到"数据库肯定比文件系统慢"这种说法时，或许值得先问一句：你测过吗？
